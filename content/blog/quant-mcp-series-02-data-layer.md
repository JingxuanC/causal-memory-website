## 实战三：两个数据源失效的完整排查（真实记录）

这次实跑遇到了两个失败，值得完整记录。

**失败 1：涨停池返回空。**

```
> get_a_limit_up_pool(date="20260929")
[]                                    ← 当天明明万科A都涨停了
> get_a_limit_up_pool(date="20260925")
[]                                    ← 换交易日还是空
```

涨停池走的是东财 `push2ex.eastmoney.com` 的 `getTopicZTPool`。指数有数据、datacenter 有数据，唯独这个域名全空——基本可判定是 **push2ex 接口变更或对本网络不可达**，而不是"今天没有涨停"。这里暴露一个设计陷阱：**接口失效和"真的没数据"返回了同样的 `[]`**。全市场截面工具 `em_clist_all` 有 `UniverseDegraded` 防护（行数低于阈值直接抛错），但涨停池这类单接口工具还没有——这是已知的改进点（你的 PR 机会）。

**失败 2：资金流接口连接被重置。**

```
> get_a_fund_flow_120d(symbol="600519")

WARNING Retrying ... Remote end closed connection without response
       (push2his.eastmoney.com/api/qt/stock/fflow/daykline/get)
```

`push2his` 的连接被对端直接断开，urllib3 按配置重试 3 次后失败。这类"软失败"平时不显眼，但它说明生产部署时最好在国内服务器跑这个服务（代码注释里写过：通达信 TCP 7709 端口对海外 IP 直接超时）。

**经验总结成三条：**

1. 免费数据源都有脾气，多源冗余比单源可靠重要——这套服务里腾讯/新浪/同花顺/东财互为备份
2. 空结果必须区分"没数据"和"坏了"，下游（尤其是 Agent）没有能力自己分辨
3. 5 分钟 TTL 的本地缓存挡掉了大部分重复请求，历史日期的数据这次 PR 之后直接永久缓存

## 缓存与限流（看懂这两个机制，排障快一半）

- **限流**：所有东财请求走 `em_get` 统一入口。原来全局 1 req/s，已改为 per-host（push2 系放宽到 0.2s），`get_a_market_snapshot` 翻 55 页从 ~70s 降到 ~12s
- **缓存**：文件缓存 + 原子换名写入，`is_empty_result` 判定为空的结果**不写缓存**（否则上游限流时返回的空 `[]` 会污染 5 分钟内所有请求）
